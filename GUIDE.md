# Как сделать MCP-сервер для ИИ-платформы

Руководство для команд, которые подключают свою систему (СЭД, учёт, справочник, CRM…) к агентам платформы.
Код — в этом репозитории (шаблон на Go), здесь — как всё устроено и что важно сделать правильно:
вход по JWT сотрудника, служебный ключ, инструменты, метки данных, файлы, подключение в консоли.

## 1. Как это устроено

```
 Сотрудник                Ваша система (СЭД, чат…)             AI Agents (платформа)             Ваш MCP-сервер            API вашей системы
     │  вопрос                    │                                    │                               │                          │
     ├──────────────────────────► │  POST /v1/agents/{agent}/runs      │                               │                          │
     │                            │  Authorization: Bearer <ключ       │                               │                          │
     │                            │                 клиента платформы> │                               │                          │
     │                            │  X-User-Token: <JWT сотрудника>    │                               │                          │
     │                            ├──────────────────────────────────► │  POST /mcp (tools/list, call) │                          │
     │                            │                                    │  Authorization: Bearer <JWT   │                          │
     │                            │                                    │   сотрудника | служебный ключ>│                          │
     │                            │                                    ├─────────────────────────────► │  Bearer <JWT сотрудника> │
     │                            │                                    │                               ├────────────────────────► │
     │                            │                                    │ ◄──── результат инструмента ──┤ ◄── данные с его правами─┤
     │ ◄──── ответ агента ────────┤ ◄──── поток NDJSON ────────────────┤                               │                          │
```

- **Ключ клиента платформы** — кто вызывает агента (ваша система). Выдаётся в консоли («Клиенты»), до MCP-сервера
  не доходит.
- **JWT сотрудника** (`X-User-Token`) — кто спрашивает. Платформа **не проверяет его подпись и не хранит**: она
  пересылает его вашему MCP-серверу как есть, а проверяет его ваш сервер (или ваша система). Поэтому агент видит
  ровно то, что сотрудник видит в системе, — права проверяет система, а не платформа.
- **Служебный ключ MCP-сервера** — постоянный секрет между платформой и вашим сервером. Задаётся в консоли у
  MCP-сервера и в настройках сервера (`SERVICE_TOKEN`).

Протокол — **MCP Streamable HTTP, версия 2025-06-18** (один эндпоинт `POST /mcp`, ответ JSON или SSE).
Платформа на каждый вызов агента открывает сессию: `initialize` → `notifications/initialized` → `tools/list` →
`tools/call`… → `DELETE` (закрыть сессию). Заголовки каждого запроса:

```
Authorization: Bearer <JWT сотрудника | служебный ключ>     (нет — при входе «без входа»)
X-Platform-Key: <служебный ключ>                             (вход токеном сотрудника, если ключ задан в консоли)
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2025-06-18
Mcp-Session-Id: <id>                                         (после initialize, если сервер его выдал)
```

Сервер может быть **stateless**: каждый HTTP-запрос несёт токен и проверяется заново — запускайте сколько угодно
копий за балансировщиком.

## 2. Вход: JWT сотрудника, служебный ключ или без входа

Способ входа выбирается в консоли у MCP-сервера и должен совпадать с `AUTH_MODE` сервера.

| Консоль | `AUTH_MODE` | В `Authorization` | Чьими правами работает сервер | Когда выбирать |
|---|---|---|---|---|
| вход токеном сотрудника | `user_token` | `Bearer <JWT сотрудника>` | **сотрудника** | почти всегда: личные данные, документы, всё, где у людей разные права |
| вход служебным ключом | `service_token` | `Bearer <служебный ключ>` | **своими** (одинаково для всех) | только общедоступное внутри организации: справочники, курсы валют, регламенты |
| без входа | `none` | — | своими, для всех | только открытые данные во внутренней сети |

### 2.1. JWT сотрудника (`user_token`)

Что приходит: `Authorization: Bearer eyJhbGciOi…` — тот же JWT, которым сотрудник вошёл в вашу систему (его
передала платформе ваша система в `X-User-Token`).

**Сервер обязан проверить токен сам.** Два способа:

1. **Спросить систему** (так делает шаблон): `GET {SYSTEM_URL}/me` с этим токеном. 200 — кто это; 401/403 — токен
   не принят. Плюс: система сама учитывает отзыв токена и блокировку сотрудника. Минус: запрос на каждый HTTP-запрос
   MCP — добавьте кэш на минуту (ключ — SHA-256 токена, **не сам токен**).
2. **Проверить подпись локально** (быстрее, если система выдаёт JWT через Infocom ID / OIDC):
   - ключи — из JWKS издателя (`/.well-known/openid-configuration` → `jwks_uri`), с кэшем и обновлением по `kid`;
   - **разрешённые алгоритмы — явно** (`RS256`/`ES256`); `alg: none` и HS-алгоритмы с публичным ключом — отказ;
   - проверить `iss` (ваш издатель), `aud` (ваша система/клиент), `exp`, `nbf` (с запасом на часы 30–60 с);
   - `sub` — id сотрудника; роли и организация — из своих утверждений токена или из системы.
   Отзыв токена локальная проверка не увидит — если это важно, оставьте и способ 1.

Дальше токен сотрудника передаётся **только в API вашей системы** (`Authorization: Bearer <JWT>`), чтобы система
отдала данные с его правами. Не используйте его для других сервисов и не храните.

Отказ — всегда **HTTP 401** (на уровне HTTP, до MCP). По 401/403 платформа понимает «токен сотрудника не принят»:
если это сервер профиля (`whoami`) или единственный сервер агента — пользователь сразу получит «войдите заново»,
иначе этот сервер просто исключается из ответа. Если система недоступна и проверить токен нельзя — **500**, а не 401
(иначе пользователя зря попросят войти заново).

Срок жизни: если JWT истёк посреди разговора — 401, система-клиент обновит токен и пришлёт новый со следующим
вопросом. Ничего не продлевайте на стороне MCP-сервера.

### 2.2. Служебный ключ

Это общий секрет платформы и вашего сервера:

- **Сгенерировать**: `openssl rand -base64 32` (не короче 32 байт случайных).
- **Положить** в двух местах: консоль → MCP-серверы → ваш сервер → «Служебный ключ» и `SERVICE_TOKEN` сервера
  (Secret в k8s через `ENV_FILE`, не в репозиторий и не в образ).
- **Сравнивать за постоянное время** (`subtle.ConstantTimeCompare` — как в шаблоне `internal/auth/middleware.go`).
- **Не логировать** ни сам ключ, ни заголовок `Authorization`.
- **Смена**: новый ключ в консоли и на сервере; на время смены сервер может принимать два ключа (старый и новый) —
  добавьте `SERVICE_TOKEN_NEXT`, если без простоя никак.

Зачем он нужен:

- **В режиме `service_token`** — это и есть вход. Сервер работает **своими** правами для всех сотрудников. Значит,
  сервер сам отвечает за то, чтобы не отдать лишнего: никаких личных данных, документов с ограниченным доступом,
  ничего, что у разных сотрудников разное. Сомневаетесь — выбирайте `user_token`.
- **В режиме `user_token`** — по желанию, **только для списка инструментов**: платформа периодически узнаёт, какие
  инструменты есть (чтобы админ мог их разрешить агентам) без сотрудника. Вызов инструмента с этим ключом сервер
  **обязан отклонить** (шаблон: `DiscoveryOnly` → ошибка) — иначе ключ стал бы «входом за всех».

Консоль хранит служебный ключ зашифрованным и никогда не показывает его обратно (только «задан / не задан»).

### 2.3. JWT сотрудника + ключ платформы (рекомендуется)

Если служебный ключ задан у сервера со входом токеном сотрудника, платформа присылает в **каждом** запросе оба:

```
Authorization: Bearer <JWT сотрудника>   ← чьи права
X-Platform-Key: <служебный ключ>        ← что запрос пришёл именно от платформы
```

Зачем: JWT сотрудника живёт у него в браузере и в вашей системе. Если он утёк, без ключа платформы с ним можно
ходить в MCP-сервер напрямую — **в обход** проверок платформы (guardrails, наблюдатель, метки данных, журнал).
С ключом сервер принимает JWT только от платформы.

Как включить:

1. Сгенерировать служебный ключ, задать его в консоли у сервера и в `SERVICE_TOKEN` сервера (раздел 2.2).
2. На сервере `REQUIRE_PLATFORM_KEY=true` (шаблон; работает только с `AUTH_MODE=user_token` и заданным
   `SERVICE_TOKEN`). Без верного `X-Platform-Key` токен сотрудника получает **401**, причём **до** запроса в систему.
3. Проверить: запрос с JWT без заголовка — 401, с заголовком — 200 (раздел 8).

Что остаётся как было: запрос с самим служебным ключом в `Authorization` (без сотрудника) по-прежнему даёт только
список инструментов. Сервер без `REQUIRE_PLATFORM_KEY` лишний заголовок просто игнорирует — включать можно по одному
серверу. Ключ платформы не заменяет проверку JWT: сервер всё так же проверяет токен сотрудника (раздел 2.1).

Если сервер не только внутренний (открыт через Ingress/шлюз наружу) — включайте обязательно.

## 3. Сервер из шаблона за 10 шагов

1. Скопируйте репозиторий `mcp-template` (без `.git`), `git init`, ветка `dev`.
2. `go.mod`: модуль `example.com/mcp-template` → `ai-platform/<имя>` (или адрес вашего репозитория), замените во всех `import`.
3. `internal/mcpserver/server.go` — название сервера и `instructions` (одна-две строки: что за система).
4. `internal/system` — клиент API вашей системы: `Me(ctx, token)` (кто это) и нужные методы. Токен — параметром
   каждого метода, никаких «запомненных» токенов.
5. `internal/tools` — свои инструменты вместо примеров `whoami`/`search_items` (раздел 4). Инструмент «кто я» оставьте —
   он нужен агенту как инструмент профиля.
6. `.env.example` → `.env` для локального запуска: `SYSTEM_URL`, `AUTH_MODE`, `SERVICE_TOKEN`.
7. Тесты: `./go.sh test -race ./...` (Go в Docker, ставить не нужно). Пример полного прогона «как платформа» —
   `internal/app/app_test.go`.
8. CI и деплой — как у сервисов платформы: `.gitlab-ci.yml` (тесты → образ в registry → деплой в k8s на ветку `dev`,
   прод по тегу кнопкой), `k8s/app.yaml` (Service без Ingress — сервер внутренний), переменные CI `ENV_FILE` и
   `KUBECONFIG`. Образец — `kyzmat-ai/tools`.
9. Подключение в консоли (раздел 7).
10. Проверка руками и вопросом агенту (раздел 8).

## 4. Инструменты

Агент — небольшая модель. Чем понятнее инструмент, тем реже она ошибается.

**Описание** (`Description`) — для модели: что делает, когда вызывать, когда *не* вызывать, что передавать, что значит
пустой ответ. По-русски, 2–4 предложения.

**Название** (`Title`) — для людей: его видно в чате, пока агент работает («Ищет документы…»), и в консоли.

```go
mcp.AddTool(s, &mcp.Tool{
	Name:        "search_documents",
	Title:       "Поиск документов",
	Description: "Ищет документы, доступные сотруднику, по номеру, краткому содержанию и датам. " +
		"Для вопроса по смыслу текста — search_document_text. Пустой список — ничего не найдено, предложи уточнить.",
	Annotations: &mcp.ToolAnnotations{ReadOnlyHint: true},
}, t.searchDocuments)
```

**Аннотации** — по ним платформа решает, что опасно:

| Аннотация | Значение | Что делает платформа |
|---|---|---|
| `ReadOnlyHint: true` | только читает | — |
| `ReadOnlyHint: false` (или нет) | меняет данные | считается «передаёт наружу» (если в консоли не указано иначе): после чтения секретного — запрет или подтверждение |
| `OpenWorldHint: true` | ходит во внешний мир (почта, внешние API) | тоже «передаёт наружу» |
| `DestructiveHint: true` | удаляет/необратимо | включите в консоли «подтверждение человеком» |

В go-sdk `DestructiveHint` и `OpenWorldHint` — указатели: `OpenWorldHint: ptr(true)` (`func ptr[T any](v T) *T { return &v }`).

**Аргументы** — мало, простые типы, понятные имена, разумные умолчания в коде (`limit` по умолчанию 10, максимум 20).
Схему go-sdk строит по структуре: `json` — имя, `jsonschema` — описание, без `omitempty` — обязательное.

**Ответ** — компактный: модель видит до ~6000 символов ответа, остальное обрезается (с пометкой). Только нужные поля,
идентификаторы (`uuid`, `id`) — обязательно: по ним агент строит ссылки и вызывает другие инструменты. Пустой
результат — `[]` и поле `note` с подсказкой.

**Ошибки** — для модели: что не так и что попробовать («Документ не найден или недоступен. Проверь номер»). Без
стектрейсов, адресов, ответов системы целиком.

**Журнал** — инструмент, исход, время, id сотрудника. Аргументы и ответы не пишите: в них личные данные.

**Изменяющие действия** (создать, отправить, подписать) — отдельными инструментами, `ReadOnlyHint: false`, в описании —
последствия («Создаёт черновик в разделе «Черновики» сотрудника. Ничего не отправляет»). Что отправляет данные
людям — в консоли включите «подтверждение человеком».

## 5. Метки данных (гриф)

Если система знает гриф данных (ДСП, секретно, служебное), передайте его платформе в `_meta` ответа инструмента:

```json
{"content": [...], "_meta": {"classification": "secret"}}
```

Уровни: `public` < `internal` < `dsp` < `secret` (другие значения игнорируются). Метку можно поставить у ответа
целиком или у отдельного элемента `content`. Платформа запоминает максимальный уровень, который агент прочитал за
вызов, и по правилу «Метки данных» в консоли (раздел «Безопасность»):

- запрещает или требует подтверждения для инструментов «наружу» (раздел 4) — секретное не уйдёт другим людям;
- не сохраняет файлы, созданные после чтения секретного;
- не пишет реплику в память разговора, скрывает текст в журнале, не делает подсказок.

В Go (go-sdk) — вернуть результат с `Meta`:

```go
func (t *Tools) getDocument(ctx context.Context, req *mcp.CallToolRequest, in getDocInput) (*mcp.CallToolResult, Document, error) {
	doc, err := t.system.GetDocument(ctx, auth.CallerOf(req).Token, in.UUID)
	if err != nil {
		return nil, Document{}, errors.New("документ не найден или недоступен")
	}
	res := &mcp.CallToolResult{}
	if level := classification(doc.Grif); level != "" { // ваш гриф → public|internal|dsp|secret
		res.Meta = mcp.Meta{"classification": level}
	}
	return res, doc, nil
}
```

Проверьте в тесте `tools/call`, что в ответе есть `"_meta":{"classification":…}`. Метка — не замена правам: доступ
к документу всё равно проверяет система по токену сотрудника.

## 6. Файлы: на вход и на выход

**На вход** (файл, который сотрудник приложил агенту). Модель видит id вида `file-…`; когда она вызывает ваш инструмент
с этим id в любом строковом аргументе, платформа подставляет вместо него **подписанную ссылку на чтение**
(S3, живёт ~10 минут). Ваш инструмент скачивает файл по ссылке:

- принимайте ссылки **только с хостов из настройки** (адрес S3 платформы, `FILES_ALLOWED_HOSTS`), не следуйте
  редиректам на другие хосты — иначе инструмент можно заставить ходить по внутренним адресам;
- лимит размера и таймаут;
- в описании аргумента: «file — id вложения (file-…) из сообщения пользователя».

Читать обычные форматы (PDF, DOCX, XLSX…) не нужно самим — для этого есть системный сервер `tools` (`read_file`).

**На выход** (инструмент сделал файл — выгрузку, отчёт, документ). Верните его встроенным ресурсом:

```json
{"content": [
  {"type": "text", "text": "Отчёт готов: 12 строк"},
  {"type": "resource", "resource": {"uri": "file:///Отчёт.xlsx", "name": "Отчёт.xlsx",
    "mimeType": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet", "blob": "<base64>"}}
]}
```

Платформа сохранит файл в своё хранилище как файл этого сотрудника, модель получит строку «Создан файл file-…», а
сотрудник — файл вместе с ответом (в чате СЭД — вложением). Ключи S3 вашему серверу не нужны. Лимит — 50 МБ.

## 7. Подключение в консоли

**Консоль → MCP-серверы → «Добавить»:**

| Поле | Что указать |
|---|---|
| Имя, название | латиница для имени (`sed`), понятное название |
| Адрес | как его видит среда агентов, с путём: `http://my-mcp:8080/mcp` (в кластере — имя Service) |
| Как агент входит | «токеном сотрудника» / «служебным ключом» / «без входа» — как `AUTH_MODE` |
| Служебный ключ | для `service_token` — обязательно; для `user_token` — рекомендуется: список инструментов без сотрудника и ключ платформы `X-Platform-Key` в каждом запросе (раздел 2.3) |
| Организация | чья система; без организации — сервер общий для всей платформы |

Дальше:

1. Инструменты появятся в карточке сервера (сразу — со служебным ключом, иначе после первого вопроса сотрудника).
   У каждого можно дополнить подсказку для модели, включить «подтверждение человеком» и задать «передаёт данные
   наружу» (авто / да / нет).
2. **Агент → «Инструменты»** — разрешить нужные. Новые инструменты сами агентам не включаются.
3. **Агент → «Настройки» → «Инструмент профиля»** — ваш `whoami`: платформа вызовет его первым, и модель сразу знает,
   кто спрашивает.
4. Проверить вопросом агенту («Эталонные вопросы» агента или чат).

## 8. Проверка руками

```bash
# список инструментов — JWT сотрудника (user_token)
curl -s https://my-mcp.example/mcp \
  -H "Authorization: Bearer $USER_JWT" -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' -H 'MCP-Protocol-Version: 2025-06-18' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'

# с REQUIRE_PLATFORM_KEY=true: JWT без X-Platform-Key — 401, с ним — 200
curl -s -o /dev/null -w '%{http_code}\n' https://my-mcp.example/mcp -H "Authorization: Bearer $USER_JWT" \
  -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'                         # → 401
curl -s … -H "Authorization: Bearer $USER_JWT" -H "X-Platform-Key: $SERVICE_TOKEN" -d '{…tools/list…}'  # → 200

# то же служебным ключом: список — да, а tools/call — должен быть отказ (в режиме user_token)
curl -s … -H "Authorization: Bearer $SERVICE_TOKEN" -d '{"jsonrpc":"2.0","id":2,"method":"tools/call",
  "params":{"name":"whoami","arguments":{}}}'

# без токена и с чужим — HTTP 401
curl -s -o /dev/null -w '%{http_code}\n' … -H 'Authorization: Bearer wrong' -d '{…tools/list…}'
```

Что должно быть: свой JWT — 200 и список; служебный ключ в `user_token` — список есть, вызов — ошибка; чужой/истёкший
JWT и неверный ключ — 401; система недоступна — 500.

## 9. Чек-лист безопасности

- [ ] Данные сотрудников — только в режиме `user_token`; в API системы уходит **его** JWT, права проверяет система.
- [ ] JWT проверяется: подпись (или запрос к системе), `iss`, `aud`, `exp`, разрешённые алгоритмы; токены не
      хранятся, не логируются, не передаются никуда, кроме API своей системы.
- [ ] Отказ во входе — 401, недоступность системы — 500.
- [ ] В `user_token` — `REQUIRE_PLATFORM_KEY=true`: JWT принимается только вместе с ключом платформы (раздел 2.3).
- [ ] Служебный ключ — случайный, ≥ 32 байт, в Secret, сравнение за постоянное время; в `user_token` он даёт только
      список инструментов.
- [ ] Ответы инструментов — без секретов, внутренних адресов, стектрейсов; только нужные поля, разумный объём.
- [ ] Массовые выгрузки персональных данных (все сотрудники с ПИН, телефонами…) инструментом не делаются.
- [ ] Гриф данных передаётся в `_meta.classification`, изменяющие инструменты помечены `ReadOnlyHint: false`.
- [ ] Ссылки на файлы скачиваются только с разрешённых хостов, с лимитами размера и времени.
- [ ] Журнал — без аргументов и ответов (личные данные).
- [ ] Сервер внутренний (без Ingress наружу), если к нему не нужен доступ извне.
