# MCP Template — шаблон MCP-сервера на Go

> Часть [ИИ-платформы](https://github.com/Keremet-Development/keremet-deploy): общая схема, стенд и список репозиториев — в keremet-deploy.

Заготовка для команд, которые подключают свою систему (CRM, учёт, справочник…) к ИИ-платформе.
Агент платформы ходит в этот сервер по **MCP Streamable HTTP** (версия протокола 2025-06-18),
получает список инструментов и вызывает их от имени сотрудника.

Внутри: go-sdk MCP v1.8.0, uber fx (у каждого пакета свой `fx.Module`), slog, Prometheus.
Два примера инструментов: `whoami` и `search_items`.

## Что где лежит

```
cmd/server/main.go        точка входа: fx.New(app.Module).Run()
internal/app              сборка приложения из модулей
internal/config           настройки из переменных окружения
internal/logger           slog в JSON
internal/system           клиент API вашей системы — ЗАГЛУШКА, замените на свои вызовы
internal/auth             проверка токена: кто вызывает (Caller) и пускать ли (ответ 401)
internal/mcpserver        MCP-сервер, HTTP-обработчик, метрики и журнал вызовов инструментов
internal/tools            инструменты: whoami (profile.go), search_items (items.go)
internal/httpserver       основной порт: /mcp, /healthz, /readyz; запуск и остановка
internal/metrics          /metrics на отдельном порту
```

Первым делом:

1. Переименуйте модуль в `go.mod` (`example.com/mcp-template` → адрес вашего репозитория) и замените его во всех `import`.
2. Поменяйте название сервера и `instructions` в `internal/mcpserver/server.go`.
3. Перепишите `internal/system` под API своей системы: как проверить токен сотрудника (`Me`) и что искать.

## Запуск

Go на машине не нужен: `./go.sh` запускает Go в Docker (кэш модулей в томе `mcp-template-go-cache`).

```bash
./go.sh test -race ./...   # тесты
./go.sh vet ./...
./go.sh fmt ./...

cp .env.example .env       # заполните SYSTEM_URL и способ входа
docker build -t my-mcp .
docker run --rm --env-file .env -p 8080:8080 -p 9090:9090 my-mcp
```

На GitHub `.github/workflows/ci.yml` проверяет gofmt, vet, тесты с -race, сборку бинарника и образа на каждый push и pull request. Задания идут на раннере организации `local`. Образ из `main` и тегов `vX.Y.Z` публикуется в `ghcr.io/keremet-development/keremet-mcp-template` — [подробнее](https://github.com/Keremet-Development/keremet-deploy#проверки-на-github).

Проверка руками:

```bash
curl -s localhost:8080/mcp \
  -H 'Authorization: Bearer <токен>' -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' -H 'MCP-Protocol-Version: 2025-06-18' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

### Настройки

| Переменная | По умолчанию | Что это |
|---|---|---|
| `SYSTEM_URL` | — (обязательна) | API вашей системы. Токен сотрудника проверяется запросом `GET {SYSTEM_URL}/me` |
| `AUTH_MODE` | `user_token` | `user_token`, `service_token` или `none` — как в консоли платформы |
| `SERVICE_TOKEN` | — | служебный ключ платформы (см. ниже) |
| `SYSTEM_TOKEN` | — | ключ сервера к системе для `service_token` и `none`; в `user_token` не используется |
| `ADDR` | `:8080` | MCP и пробы |
| `MCP_PATH` | `/mcp` | путь MCP-эндпоинта |
| `METRICS_ADDR` | `:9090` | `/metrics`; пусто — не отдавать |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |
| `SYSTEM_TIMEOUT` | `15s` | сколько ждать систему |
| `SHUTDOWN_TIMEOUT` | `20s` | сколько ждать текущие запросы при остановке |

Пробы: `/healthz` — процесс жив; `/readyz` — запущен и не останавливается
(место для проверки доступности системы — комментарий в `internal/httpserver/health.go`).
Метрики инструментов: `mcp_tool_calls_total{tool,status}`, `mcp_tool_call_duration_seconds`.

## Как подключить к платформе

В консоли платформы: **MCP-серверы → добавить**.

- **Адрес** — как его видит среда агентов (RAG) из своей сети, вместе с путём: `http://my-mcp:8080/mcp`.
- **Как агент входит** — тот же режим, что `AUTH_MODE` сервера:

| В консоли | `AUTH_MODE` | Что присылает платформа | Что делает сервер |
|---|---|---|---|
| вход токеном сотрудника | `user_token` | `Bearer <токен сотрудника>` — то, что вызывающий передал в `X-User-Token` | проверяет токен в системе (`GET /me`), работает с правами сотрудника |
| вход служебным ключом | `service_token` | `Bearer <служебный ключ>` из консоли | сравнивает с `SERVICE_TOKEN` |
| без входа | `none` | ничего | пускает всех — только для внутренней сети и открытых данных |

- **Служебный ключ** при входе токеном сотрудника — по желанию. Если задать его в консоли и в `SERVICE_TOKEN`,
  платформа сама периодически узнаёт список инструментов. Этим ключом можно только получить список:
  вызов инструмента с ним вернёт ошибку. Без ключа инструменты появятся в консоли после первого вопроса сотрудника.
- Новые инструменты не включаются агентам сами: их надо разрешить в настройках агента.
- **Инструмент профиля.** В настройках агента укажите `whoami`. Платформа вызовет его первым и положит ответ в промпт, так что модель сразу знает, кто спрашивает. Если сервер ответит 401, агент сразу вернёт «токен не принят» и не будет тратить модель.

Отказ во входе — всегда **HTTP 401**: по 401/403 платформа понимает «токен не принят».
Если система недоступна и токен проверить нельзя, сервер отвечает 500 — это не «токен не принят».

Каждый HTTP-запрос к MCP проверяет токен заново, сессий сервер не хранит (stateless) — его можно запускать
в нескольких экземплярах за балансировщиком. Если `GET /me` дорогой, добавьте короткий кэш в `internal/auth/middleware.go`.

## Как добавить инструмент

1. Если нужен новый вызов системы — метод в `internal/system` (например, `GetItem`).
2. В `internal/tools` — входная структура, выходная структура и обработчик:

```go
type getItemInput struct {
	ID string `json:"id" jsonschema:"id записи из search_items"`
}

func (t *Tools) getItem(ctx context.Context, req *mcp.CallToolRequest, in getItemInput) (*mcp.CallToolResult, system.Item, error) {
	item, err := t.system.GetItem(ctx, auth.CallerOf(req).Token, in.ID)
	if err != nil {
		return nil, system.Item{}, errors.New("запись не найдена или недоступна") // это увидит модель
	}
	return nil, item, nil
}
```

3. Строка регистрации в `Register` (или в своём `registerXxx`):

```go
mcp.AddTool(s, &mcp.Tool{Name: "get_item", Description: "...",
	Annotations: &mcp.ToolAnnotations{ReadOnlyHint: true}}, t.getItem)
```

Схему аргументов go-sdk строит по полям структуры сам: `json` — имя, `jsonschema` — описание поля,
поле без `omitempty` — обязательное. Ошибка из обработчика уходит модели как ошибка инструмента (`isError`).

Большая группа инструментов — отдельный пакет со своим модулем:
`fx.Module("orders", fx.Provide(mcpserver.AsToolset(NewOrderTools)))` и строка в `internal/app/app.go`.

## Как писать инструменты для небольших моделей

- **Описание — конкретное**: что делает, когда вызывать, когда *не* вызывать, что писать в аргументы,
  что значит пустой ответ. Пример — `search_items` в `internal/tools/items.go`. Подсказку к инструменту
  можно дополнить и в консоли платформы, не меняя сервер.
- **Мало аргументов**, простые типы, понятные имена. Значения по умолчанию — в коде, а не на совести модели.
- **Компактный ответ**: в контекст модели попадает примерно 6000 символов результата, остальное обрезается.
  Отдавайте только нужные поля, ограничивайте число записей (`limit` до 20), длинные тексты — коротко или отдельным инструментом.
  Пустой список — `[]` и подсказка, что делать дальше (поле `note`).
- **Ошибки — для модели**: что пошло не так и что попробовать. Без адресов, стектрейсов и ответов системы целиком.
- **Никаких секретов в ответе и в тексте ошибки**: токены, ключи, пароли, внутренние адреса. Ответы инструментов
  платформа проверяет на prompt injection, но утечку секрета это не отменяет.
- Помечайте инструменты только для чтения: `ReadOnlyHint: true`. Изменяющие — отдельными инструментами
  с явным описанием последствий.
- В журнал сервера аргументы и ответы не пишутся (там могут быть личные данные) — только инструмент, исход, время и id сотрудника.

## Тесты

- `internal/auth/middleware_test.go` — все режимы входа: принят, чужой токен, без заголовка, служебный ключ, система недоступна.
- `internal/app/app_test.go` — приложение целиком с поддельной системой (httptest): `initialize`,
  `notifications/initialized`, `tools/list`, `tools/call`, `DELETE` — те же запросы и заголовки, что шлёт платформа;
  служебный ключ видит список, но не вызывает инструменты; неверный токен — 401.
